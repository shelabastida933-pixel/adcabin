## 为什么必须用 API，而不是在后台点

在后台手动操作能做的事，用 API 都能做，而且有三个后台给不了的能力：

- **跨账户聚合**——后台一次只能看一个账户；API 可以把几十个账户拉成一张表

- **自动化执行**——定时任务、批量操作、秒级响应，人做不到

- **可编程的诊断**——把「消耗 ÷ 激活」这类自定义指标算出来，后台不提供

但代价是：**文档不会告诉你字段的真实行为。**下面 9 个坑，全部来自"文档看起来没问题但实际跑不通"的情况。

## 九个个真实报错

1

### 返回字段是 `accounts` 而不是 `list`

现象

调用账户列表接口，返回看起来是空数据或结构错误，拿不到子账户。换了好几个接口名都没用。

```
调用 customer_center_account_list_v3
预期取：data.list
实际应取：data.accounts
```

原因

不同版本的账户列表接口返回结构不统一。文档示例用的是 `list`，
 但 `v3` 版本返回的键名是 `accounts`。你用旧的解析逻辑去取，自然拿到空值。

解法

解析时做兼容：`data.accounts || data.list || []`。
 更重要的是**先用一个账户把返回的完整 JSON 打出来看一眼**，
 而不是照着文档写解析——这一步能省掉大量的猜测。

2

### 极速智投的计划根本不能改出价

现象

调用更新出价的接口，被系统直接拒绝：

```
自动投放单元不能包含出价参数
```

原因

这类计划属于**极速智投（自动投放）**，出价由系统托管，不开放手动修改。
 而另一条同时出现的报错是：

```
不支持搜索周期稳投广告修改出价
（对应 delivery_type=DURATION）
```

也就是说：**同一个"改出价"动作，在不同投放类型下有不同的权限边界。**

解法

动出价之前，先读计划的 `delivery_type` 和投放模式：
 自动投放 / 周期稳投都不支持改价。

 这类计划想提升量级，正确做法是**从素材侧下手**（补新素材、扩标题），
 而不是硬改出价。

3

### "加预算"根本无从下手——它本来就是无限预算

现象

计划跑不出量，第一反应是加预算，结果发现：

```
budget_mode = BUDGET_MODE_INFINITE
```

原因

这是**不限预算**模式——预算由账户余额兜底，计划层级根本没有"预算上限"这个可调项。
 所谓"加预算"这条路走不通。

解法

先读 `budget_mode`。如果是不限预算，说明**限制因素不在预算**，
 要去查：出价是否有竞争力、定向是否过窄、素材是否老化、关键词池是否太小。

这一条我印象很深：当时我以为发现了"余额充足却跑不出去"，其实账户余额一千多、
 日耗只有十几块——**不是没钱，是花不出去**。这是完全不同的问题。

4

### 更新素材列表报错：「请填写 carousel_id 或 item_id」

现象

只想往单元里补几个视频素材，调用更新接口后报错：

```
请填写carousel_id或item_id
```

但你看自己的请求体，明明只传了 `video_material_list`，压根没打算碰轮播素材。

原因

关键发现：这个单元**本来就有 8 条 `carousel_material_list`**（图文+音频的轮播素材），
 加上 4 条 `video_material_list`。

更新接口是**整体覆盖语义**——你只传 `video_material_list`，
 等于告诉系统"这个单元的素材只有这些"，系统就要求你同时给出轮播素材的标识。

解法

**修改前必须先读完整素材列表，合并后再整体提交。**

```
# 错误做法
payload = {"video_material_list": [...]}

# 正确做法：先读，再合并
cur = get_unit(unit_id)
payload = {
    "video_material_list":   cur["video_material_list"] + new_videos,
    "carousel_material_list": cur["carousel_material_list"],  # 原样带回
}
```

顺带一个相关坑：轮播素材里的 `item_id` 可能是 `null`，
 而 `material_id` 有值；还有一个元素带着 `item_id: 0`。
 **不能简单地把 null 当作"没这个字段"来清理。**

5

### 读取接口拿到的 null，直接提交会被拒

现象

从读取接口拿到对象后原样改一改再提交，报：

```
dpa_word_list 不能为 null
```

原因

读取接口会把未设置的字段返回为 `null`。
 写入接口对这些字段**不接受 null**——它要的是"字段不存在"或"空数组"。

解法

写入前做一次深度清理：**递归剔除所有值为 `null` 的键**。
 但要注意例外（见坑 4）：像 `item_id: null` 这种在特定数组元素里可能有语义，
 不能一律删。

```
def strip_nulls(o):
    if isinstance(o, dict):
        return {k: strip_nulls(v) for k, v in o.items() if v is not None}
    if isinstance(o, list):
        return [strip_nulls(x) for x in o]
    return o
```

6

### 「建了项目没建单元」——计划永远零消耗

现象

批量建了一批计划，项目（campaign）状态是 `ENABLE`，看起来一切正常，
 但消耗始终是 `¥0`。

原因

巨量引擎是**三层结构**：项目 → 单元 → 素材。
 只建了项目、没建单元，等于**没有可投放的实体**，自然不会跑。

解法

建计划的流程必须完整：创建项目 → **创建单元** → 挂载素材。
 排查零消耗账户时，"有没有单元"应该是最先检查的一项。

这个坑的实际代价很大：我一度有 32 个账户处于零消耗状态，
 其中相当一部分就是这个原因——**不是账户有问题，是计划结构不完整。**

7

### 工具列表只返回 2 个工具

现象

调用 `tools/list` 只拿到 2 个工具，而你以为应该有几十个接口可用。

原因

这是 **Tool-Range 限制**——授权的工具范围是有限的，
 不是"拿到 token 就能调所有接口"。

解法

不要指望工具列表能告诉你全部能力。
 **直接按接口名去试**，并准备好处理"权限不足"这一类错误码。

记住

权限边界是项目开始前就必须确认的第一件事，
 而不是写到一半才发现某个关键接口没权限。

8

### 小程序 ROI 指标要单独找，名字很长

现象

想拉 ROI，但配置里查不到 `cpc` / `cpm` 这类常见指标名，
 拉出来的数据没有 ROI 字段。

原因

巨量引擎针对**小程序类落地页**有一套专门的归因指标，
 命名带 `attribution_` 前缀，例如：

```
attribution_micro_game_0d_roi
attribution_micro_game_7d_roi
attribution_active_pay_intra_on...
```

解法

不要靠猜指标名。**先把账户可用的指标清单拉出来看一遍**，
 再按业务需要挑选。小程序类账户尤其要关注 `attribution_` 系列——
 它们直接反映付费回收。

> **⚠️ 一个容易误判的信号**

> 如果你发现所有 ROI 指标都是 `0`，先别急着下"投放没效果"的结论。
 **更可能是付费回传链路没通**——用户付费了但没回传给广告平台，
 模型学不到"谁会付费"，量自然起不来。这是数据链路问题，不是投放问题。

9

### 定时任务里不能执行代码

现象

把脚本做成定时任务后，原本能跑的动态执行功能报错，提示当前模式下不可用。

原因

定时任务运行在**受限的纯脚本模式**下，出于安全考虑禁用了动态执行能力。

解法

定时任务里的逻辑必须**全部预置成静态代码**，
 不能依赖运行时动态生成。好处是：纯脚本任务不消耗对话 token，可以放心高频跑。

## 一张表总结：动之前先读什么

| 你想做的事 | 必须先读的字段 | 可能的阻挡 |

|---|---|---|

| 改出价 | `delivery_type`、投放模式 | 自动投放 / 周期稳投不支持 |

| 加预算 | `budget_mode` | 不限预算模式下没有预算可加 |

| 换素材 | 完整素材列表（video + carousel） | 整体覆盖语义会丢掉未传的素材 |

| 批量建计划 | 项目/单元层级是否完整 | 只有项目没有单元 → 零消耗 |

| 拉 ROI | 可用指标清单 | 小程序指标命名不同；ROI 全 0 可能是回传未通 |

| 提交更新 | 请求体里的 null | 写入接口不接受 null 字段 |

## 最重要的三条经验

> **1. 先读，再写**

> 所有写入操作之前，先把当前完整状态读出来。**巨量引擎的更新接口多数是整体覆盖语义**，
 只传一部分字段 = 把其他字段清空。

> **2. 每次写入后回读验证**

> 接口返回成功不代表生效。写入后立刻回读一次，确认值真的变了。
 我靠这个习惯抓到过好几次"报错但其实部分成功"的情况。

> **3. 把返回的原始 JSON 打出来**

> 文档和实际返回不一致是常态（见坑 1）。
 **不要照着文档写解析，照着真实返回写。**

## 关于 API 权限

最后提醒一件比技术更重要的事：**权限边界要在项目开始前确认清楚。**

你需要先搞清楚自己的权限类型——是自有主体的账户授权，还是服务商资质。
 这两者能操作的账户范围完全不同。如果是给客户做，还要确认代操作他人账户是否在授权范围内。

> **⚠️ 别跳过这一步**

> 技术上跑通、业务上违规，是最贵的错误。
 先确认边界，再写代码。
